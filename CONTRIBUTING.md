# Работа с исходниками Slynor

Перед любым изменением следовать [ТЗ](Slynor_TZ_v0.1_RU.md) и [этапу 0](docs/STAGE0_WINDOWS_RU.md).
До первого git add: проверить ignore, dry-run и staged diff. Не использовать разрушительную очистку Git.
Новые изменения оформлять небольшой веткой/коммитом. Непроверенный EXE не маркировать stable.

## Окружения

Python 3.13 x64 и нативные компоненты устанавливаются разработчиком с проверкой происхождения.
Создавать окружения только в НОВОМ clone. Кандидаты: [requirements](requirements/README.md).
GUI, provider, search, build и будущий bot/service разделены; не устанавливать всё в одну venv.
Наблюдавшиеся constraints не подтверждены свежей установкой. После Windows-валидации нужны полный lock,
хеши wheel и нативных redistributable; затем переключение установочных и сборочных сценариев отдельным изменением.

## Проверки

```powershell
py -3.13 tools/stage0_audit.py
.\.venv\Scripts\python.exe -m pip check
.\.providers\Scripts\python.exe -m pip check
.\.search\Scripts\python.exe -m pip check
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

Тесты с двойниками VLC и API проверяют контракты. Они не подтверждают звук и работу источников.
`python -m unittest discover -s tests -p test_stage0_audit.py -v` и `test_stage20.py` работают без GUI-зависимостей.
UI-прогоны tools/test_stage*.cjs требуют Playwright и ожидаемых локальных маршрутов; проверять конкретный
скрипт до запуска. package.json/Node lock и текущего закреплённого Playwright в проекте нет: воспроизводимость UI пока не принята.
Не устанавливать `latest` через npx для отчёта о фиксированном окружении.

Сеть не входит в воспроизводимый CI: методика live-эксперимента — `docs/experiment/PLAN_RU.md` (локально, не публикуется).
Первые полезные результаты оцениваются вручную; HTTP 200 не равен релевантности и полному аудио.

## Секреты и данные

Токены и cookies задаются локально/через согласованное хранилище, не во frontend, Git, отчётах, командной строке
и не в логах signed URLs. Не передавать чужие cookies и не обходить доступ.
Аудитор выводит только категории и положения подозрительных данных. Семь исходных тестовых строк с фиктивными
credentials просмотрены отдельно; исключение привязано к хешу строки и не распространяется на новые секреты в tests.
Перед push необходимы ручной просмотр и актуальный поддерживаемый secret scanner. Публичный remote не создаётся этим комплектом.
При реальной утечке сначала отозвать ключ; удаление одной строки из последнего коммита недостаточно.

## Сборка, backup и восстановление

[BUILD_PORTABLE_STAGE23](docs/BUILD_PORTABLE_STAGE23.md) — сохранённый рецепт, не проверенный выпуск.
Не запускать BUILD.cmd/BUILD_WINDOWS.ps1 в исходной рабочей папке: они очищают старый dist и .buildenv.
Нативные bundle, лицензии и SHA-256 предоставляются отдельно, а не берутся из venv разработчика.
Чистая Windows и реальные аудиоисточники проверяются отдельно от Linux/Chromium.

Backup включает исходники, оригинальный ZIP, всю рабочую dist и LOCALAPPDATA при закрытом плеере.
[Проверить копии хешами и восстановить в отдельную папку](docs/STAGE0_WINDOWS_RU.md); до отдельного решения не перезаписывать действующие данные.
Локальный Git хранит код. Для контрольного восстановления кода clone должен работать без файлов личного ПК.
