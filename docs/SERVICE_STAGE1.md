# Music Service: вертикальный срез этапа 1

Часть ТЗ §2: одна логика поиска и получения аудио для плеера и будущего Telegram-бота.
Сейчас есть каркас, адаптер источников, измеряемое хранилище файлов и задания
«поиск → кандидат → скачивание → доставка». Telegram-бота, кеша с TTL и
аутентификации ещё нет; сервис слушает только loopback.

## Что внутри

| Модуль | Ответственность |
|---|---|
| `errors.py` | `ServiceError` и стабильные машинные коды; текст без секретов и подписанных URL |
| `worker.py` | один JSON-запрос к изолированному обработчику: жёсткий срок, предел ответа, allowlist окружения |
| `providers.py` | `ProviderTrack`, стабильные идентификаторы, публичные страницы, `WorkerProvider` поверх `backend/provider_worker.py` |
| `media.py` | SHA-256, размер, контейнер, кодек и измеренная длительность файла (PyAV, без догадок) |
| `assets.py` | хранилище по хешу: `assets/<ab>/<sha256>.<ext>`, видимые лимиты, проверка пути |
| `delivery.py` | `FileDeliverySink`: выдача ассета в папку `outbox` с боковым JSON; контракт для будущего Telegram |
| `pipeline.py` | обработчики заданий: поиск, скачивание, доставка |
| `models.py` | `Recording`, `AudioCandidate`, `AudioAsset`, `Job`, `Delivery`; строгая валидация |
| `db.py` | SQLite WAL, схема v1, репозитории без ORM |
| `jobs.py` | персистентная очередь, повторы, отмена, один диспетчер |
| `api.py` | локальный FastAPI: здоровье, провайдеры, лимиты, задания, запись с кандидатами, ассеты, доставки |
| `__main__.py` | `python -m service`: сборка реального конвейера и запуск uvicorn |

Сервис не импортирует yt-dlp, spotDL или SCDL. Он вызывает уже существующий
изолированный обработчик плеера (`.providers`), поэтому парсер источника остаётся
в репозитории один. Идентификатор записи в базе — стабильный ID (например, 11 символов
видео YouTube), а не истекающая ссылка на медиа. Правило разбора ссылок продублировано
тестом, который сверяет его с `backend.provider_worker.validate_track_url`.

## Поток одного задания

1. `POST /jobs {kind:"search", payload:{query, provider?, limit?}}`
   → `Recording` + `AudioCandidate` (повтор не создаёт дубль), в результате стабильные
   идентификаторы, длительность из каталога, публичная страница и предупреждения источника.
   `availability` остаётся `unknown`: карточка каталога не доказывает наличие аудио.
2. `POST /jobs {kind:"download", payload:{candidate_id, audio_format?}}`
   → файл скачивается в приватную папку, измеряется и публикуется как `AudioAsset`
   с SHA-256; одинаковые байты хранятся один раз.
3. `POST /jobs {kind:"deliver", payload:{asset_id, target:"telegram:<id>"}}`
   → `Delivery`; повтор для той же пары «ассет + адрес» не отправляет файл снова.

## Запуск

```powershell
python -m service --port 8766 --proxy http://127.0.0.1:10809
python -m service --db "$env:TEMP\service-test.sqlite3" --api-only
```

Обработчику нужен изолированный интерпретатор из `.providers` (из него берутся
yt-dlp/spotDL/SCDL); другой путь задаётся `OWNPLAYER_PROVIDER_PYTHON`.
`--proxy` передаётся обработчику явно: сервис не наследует системный прокси и не
читает `network.json` плеера. `--api-only` поднимает API без выполнения заданий.

Данные по умолчанию — папка рядом с базой, `%LOCALAPPDATA%\Slynor\service`:
`service.sqlite3`, `assets/`, `work/`, `outbox/`. `--db` или `SLYNOR_SERVICE_DB`
меняют расположение целиком.

## API

| Метод | Путь | Смысл |
|---|---|---|
| GET | `/health` | статус, версия схемы, WAL, счётчики заданий, подключён ли диспетчер |
| GET | `/providers` | подключённые источники и их реальные операции |
| GET | `/limits` | пределы файла и хранилища с текущим расходом |
| POST | `/jobs` | поставить задание; ответ 201 |
| GET | `/jobs?status=&limit=` | последние задания |
| GET | `/jobs/{id}` | одно задание |
| POST | `/jobs/{id}/cancel` | отменить только задание в очереди |
| GET | `/recordings/{id}` | запись и её кандидаты |
| GET | `/assets/{id}` | измеренный файл |
| GET | `/deliveries?asset_id=` | доставки ассета |

Реализованы виды `search`, `download`, `deliver`. `resolve` и `convert` пока без
обработчика: такое задание завершается ошибкой «Нет обработчика», а не висит.

## Гарантии и лимиты

- Задание коммитится до начала работы и переживает перезапуск; захват атомарный,
  `attempts` растёт при захвате, `fail` возвращает в очередь до `max_attempts`.
- Диспетчер один; обработчики не выполняются под блокировкой очереди.
- Ошибка задания хранит тип и машинный код, например
  `ProviderError: unknown_candidate: Кандидат не найден.`.
- Файл становится `AudioAsset` только после измерения; имя задаёт SHA-256,
  путь относительный, выход за корень хранилища отклоняется.
- Лимиты видимы и не приводят к тихому удалению: 200 МиБ на файл и 2 ГиБ на
  хранилище по умолчанию; при отказе в тексте реальные числа.
- Вызов обработчика: запрос ≤ 12 000 байт, ответ ≤ 160 КиБ, срок поиска 20 с,
  resolve 15 с, скачивания 600 с; по истечении процесс убивается.
- Доставка идемпотентна по паре «ассет + адрес»; неудачная попытка помечает ту же
  запись `failed`, второй строки не появляется.
- Отмена по-прежнему возможна только для `queued`; выполняющееся задание не прерывается.

## Проверено

- `521` unittest (50 новых на провайдеров, измерение, хранилище и конвейер), 12 skipped.
- Живой прогон на этой Windows 2026-10-28 через реальный сервис и `.providers`:
  поиск «Пошлая Молли» — 5 строк с устойчивыми ID; resolve вернул поток
  `*.googlevideo.com`; скачивание — webm/opus, 3 166 041 байт, измерено 205 221 мс
  при каталоге 206 000 мс; доставка в `outbox` с боковым JSON.
- Контейнеры mp3 и webm/opus измерены на локально сгенерированных файлах (FFmpeg),
  без чужого аудио.
- Не доказано: релевантность выдачи, выбор основного и резервного источника,
  сеть с VPS в РФ, Windows GUI, Telegram, перезапуск под нагрузкой.

## Ограничения и следующий шаг

- Поиск возвращает метаданные как есть: в выдаче встречаются длинные сборники
  («плейлист …», 26–27 минут). Сервис их не отфильтровывает молча — правила качества
  должен дать обязательный эксперимент источников (ТЗ §4). Подсказки версии
  (live/remix/cover) пока не заполняются.
- Прямой поток (`resolve`) поддерживается только для YouTube; Spotify и SoundCloud
  доступны как поиск и скачивание, но живьём не проверялись.
- Один диспетчер означает одну загрузку одновременно; ТЗ §6 допускает до двух.
  Ограниченный пул — следующая работа вместе с ботом.
- Telegram-приёмник, aiogram, allowlist, `file_id`-кеш, TTL и очистка кеша не
  добавлены; аутентификация отсутствует, поэтому только loopback.
- `requirements/service.txt` не создан: сервис использует FastAPI/Pydantic из
  GUI-набора, PyAV — для измерения.
- Миграций по-прежнему нет, только версия схемы.
