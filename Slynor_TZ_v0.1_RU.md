# Slynor — техническое задание и план развития

**Статус:** проект ТЗ v0.1 для согласования. Это план, не отчёт о реализации. Код, Git-репозиторий и содержимое проекта этим документом не изменяются.

## 1. Цели и исходные условия

Создать личную музыкальную экосистему: Telegram-бот для поиска и получения разрешённого аудио → тот же бот на небольшом сервере → интеграция с Windows-плеером → надёжный и отзывчивый интерфейс → автономные установщик и portable. В дальнейшем: рекомендации, синхронизация с Android.

Условия:
- Сначала Windows x64; Android — отдельный будущий этап.
- Бот сначала работает на домашнем ПК и доступен только при включённом процессе и наличии интернета. Локальный запуск бота не означает работу Telegram без интернета.
- Затем сервер в РФ для владельца и нескольких приглашённых пользователей. Минимальный разумный бюджет, без обязательных GPU, Kubernetes и нескольких баз данных.
- Основной формат для плеера — исходная доступная аудиодорожка; MP3 по выбору. Повышение битрейта не превращает низкокачественную запись в качественную.
- Не вводить произвольное продуктовое ограничение количества сохранённых песен. Ресурсные лимиты запросов, кеша, загрузок и очередей необходимы и должны быть видимыми, без молчаливого обрезания.
- Существующий стек плеера: Python, pywebview, HTML/CSS/JavaScript, локальный FastAPI, LibVLC. Сохранять работающие функции и общий визуальный характер; не переписывать всё ради смены технологий.
- Переданный ранее этап 23 — кандидат исходников. Его Linux/Chromium-тесты не подтверждают готовность Windows-релиза, реальных источников или автономной упаковки.

## 2. Принцип архитектуры

**Одна логика поиска и получения аудио, несколько интерфейсов.** Бот и desktop не должны независимо реализовывать одинаковые парсеры и правила сопоставления.

```text
Telegram ── aiogram-бот ─┐
                        ├─ Music Service ─ адаптеры метаданных и аудио
Windows ── API-клиент ───┘       │
                                ├─ база: задания, пользователи, каталог
                                └─ ограниченный кеш файлов / изолированные воркеры
```

На старте Music Service и бот — локальное приложение с отдельным процессом тяжёлых заданий. После переноса на сервер интерфейсы и контракты сохраняются. Локальный режим плеера остаётся доступным независимо от сервера.

Разделить сущности:
1. **Recording** — музыкальная запись: название, исполнители, длительность, версия, внешние идентификаторы, происхождение метаданных.
2. **AudioCandidate** — конкретный доступный источник аудио, предполагаемая версия, длительность, оценка соответствия и состояние доступности.
3. **AudioAsset** — фактически полученный файл: контейнер, кодек, хеш, размер, фактическая длительность, происхождение, местоположение.
4. **Job** — поиск, получение ссылки, скачивание, конвертация, доставка; отдельные этапы и ошибки.
5. **Delivery** — доставка результата конкретному пользователю/устройству и подтверждение сохранения.

Нельзя считать название в каталоге доказательством наличия полной аудиозаписи. Нельзя сохранять истекающий URL потока как постоянный идентификатор песни.

## 3. Рекомендуемый стек

| Область | Решение | Обоснование |
|---|---|---|
| Язык основного сервиса | Python 3.13 x64; версии зависимостей фиксируются после проверки | Совместимость с текущим desktop; одна основная экосистема |
| Telegram | aiogram 3.x, long polling | Асинхронный бот, локальный запуск без публичного входящего порта |
| Сервисный API | FastAPI + Uvicorn + Pydantic, отдельный от desktop API | Контракт для плеера и будущего Android |
| HTTP | httpx, повторно используемые клиенты, таймауты и ограничение параллельности | Не создавать соединения бесконтрольно |
| Каталог и задания | SQLite WAL + SQLAlchemy 2.x + Alembic | Небольшое число пользователей; миграции и восстановление |
| Очередь MVP | Персистентная таблица jobs, один исполнитель/диспетчер, ограниченный пул изолированных процессов | Не терять задания при перезапуске; без Redis/Celery на старте |
| Поиск локальной библиотеки | SQLite-индексы / FTS5 после проверки сборки SQLite | Быстрый поиск без полного чтения JSON при каждом действии |
| Аудио | yt-dlp, FFmpeg/ffprobe; Deno + yt-dlp-ejs для соответствующего адаптера | Контролируемый набор инструментов, а не десяток конкурирующих загрузчиков |
| Метаданные/теги | Адаптеры каталогов, MusicBrainz; Mutagen, обложки с проверенным происхождением | Отделить красивую карточку от получения аудио |
| Desktop | Сохранить pywebview + HTML/CSS/JS и LibVLC; модульный frontend | Нет основания для немедленного перехода на Electron/React/Qt |
| Доставка на сервер | Linux, Docker Compose, persistent volumes, один экземпляр polling-бота | Повторяемый перенос и восстановление |
| Публичный API | Caddy + HTTPS, аутентификация устройств | Не публиковать локальный VLC/desktop API |
| Тесты | Сохранить unittest; добавлять pytest/pytest-asyncio по необходимости, Playwright, фикстуры | Не переписывать работающие тесты ради унификации |
| Профилирование | perf_counter, py-spy, cProfile, WebView2 DevTools, Windows PerfMon | Сначала определить узкое место, потом оптимизировать |
| Качество и релизы | Git/GitHub, Ruff, выбранный type checker, CI Linux + Windows | Проверяемая история и воспроизводимые выпуски |
| Windows-пакет | PyInstaller onedir + приватные runtime + Inno Setup | Распаковал/установил и запустил, без системного Python |

PostgreSQL вводить при реальной потребности в нескольких записывающих сервисах и более высокой нагрузке. Redis — только при доказанной необходимости распределённой очереди. SQLite хранить на локальном persistent volume, не на сетевой папке; резервировать через корректный SQLite backup/снимок с учётом WAL.

В чужих языках возможны адаптеры, но для MVP не добавлять Node.js/Go/Rust без конкретной пользы. Изолированный CLI с JSON по stdin/stdout либо внутренний HTTP API обычно проще сопровождать, чем FFI. Вызовы через shell и произвольные пользовательские аргументы запрещены. Вынос процесса не отменяет лицензионных обязательств.

## 4. Проверка источников и библиотек — обязательный этап до бота

### 4.1. Выбранная основа и кандидаты

- **yt-dlp** — основной кандидат получения доступного аудио, не гарантия работы всех сайтов. Документация рекомендует FFmpeg/ffprobe и JS-компоненты для соответствующих источников. [^https://github.com/yt-dlp/yt-dlp]
- **SomeDL** — реальный проект: получает аудио через yt-dlp и добавляет метаданные из других источников. Поэтому не является независимым способом устранить отказ YouTube. У проекта GPL-3.0; перед включением проверить лицензионную совместимость, управляемость конвертации и API. В обязательный runtime MVP не включать до эксперимента. [^https://github.com/ChemistryGull/SomeDL]
- **spotDL** — существующий кандидат сопоставления каталожных записей с доступным аудио; не считать его способом получить исходный мастер Spotify. Оставлять только при пользе, подтверждённой тестом соответствия и зависимостей.
- **MusicBrainz** — дополнительный источник идентификаторов и метаданных, не файлов музыки. Соблюдать User-Agent, кеширование и опубликованный лимит: не более одного запроса в секунду на приложение. Не блокировать на нём первую поисковую выдачу. [^https://musicbrainz.org/doc/MusicBrainz_API]
- **musicdl** — реальный Python-агрегатор. Провести эксперимент только с нужными адаптерами, проверить их зависимости, лицензии, удалённые API, авторизацию и доступность с выбранной сети. Список поддерживаемых платформ не равен подтверждённой работоспособности в нашем случае. Не включать все платформы автоматически. [^https://github.com/CharlesPikachu/musicdl]
- **music-lib (guohuiyuan)** — найден конкретный Go-проект, лицензия AGPL-3.0. Рассматривать как дополнительный адаптер только после проверки нужного провайдера и лицензионных условий; не делать обязательной частью Python/Windows-сборки. [^https://github.com/guohuiyuan/music-lib]
- **msoc** — уже присутствует в проекте как изолированный резервный компонент. Его фактическую пользу надо оценивать на тех же запросах, а не считать автоматически быстрым основным поиском.
- **SaavnAPI, Class163-NexT, cloudmusic, didban, ramdl, yamuse, kojioka, kyrie-core, @zibot/scdl, usegolib, rustbridge** и другие названия из предложенного списка не включать в обязательный стек по описанию. Точные проекты/версии и заявленные свойства не подтверждены этой проверкой; для выбора нужны ссылки на конкретные репозитории. Существование одноимённого проекта не доказывает доступность аудио и совместимость.

Задача не выбрать «самую быструю библиотеку вообще», а получить 1 основной и 1 независимый резервный путь с измеренной полезностью. Две оболочки над одним YouTube-загрузчиком не являются независимыми источниками.

### 4.2. Эксперимент

Подготовить фиксированный набор не менее 50 запросов: русские/зарубежные исполнители, кириллица/латиница, одинаковые названия, live/remix/cover, короткие и длинные записи, недоступные треки. В список реальных загрузок включать только записи, на скачивание которых есть право; остальные проверять на уровне метаданных/доступности.

Для каждого адаптера фиксировать:
- первый и повторный поиск; время первого полезного результата и завершения;
- соответствие исполнителя, длительности и версии записи;
- наличие полного аудио или только preview;
- длительность resolve/download/conversion/delivery отдельно;
- долю успехов, категории ошибок, использование CPU/RAM, необходимость входа/подписки;
- результат с домашней сети и с тестового VPS в РФ;
- лицензию, точную версию, происхождение и доступность без сторонних платных посредников.

Предварительный критерий выбора: не менее 90% релевантных карточек в доступной части согласованного набора; не менее 95% успешных загрузок среди действительно разрешённых и доступных полных файлов. Это цели эксперимента, не текущий результат и не обещание покрытия всего музыкального каталога. Ручную оценку качества отделять от технической успешности HTTP-запроса.

Низкое соответствие — предложить альтернативы. Не выдавать автоматически cover/live или 30-секундный preview за выбранную полную студийную запись. Не обещать версию «без цензуры» только по названию или флагу метаданных.

## 5. Этап 0 — безопасная база проекта

Результат: резервная копия, чистое дерево исходников, Git-история и воспроизводимое окружение.

1. Закрыть плеер; сохранить исходники и пользовательские данные `%LOCALAPPDATA%\\OwnPlayerMusic`, включая скачанные файлы и плейлисты.
2. Сохранить переданный оригинальный ZIP вне репозитория. Не стирать единственную рабочую Windows-сборку.
3. Создать локальный Git-репозиторий и приватный GitHub remote после проверки секретов. Git работает без GitHub; откаты возможны локально.
4. Проверить .gitignore до первого git add. Снять baseline работающего состояния, отдельно коммитить ранее полученный этап 23, не обозначать непроверенный EXE как стабильный релиз.
5. Сохранить существующие тесты, инструменты и графические assets. Разнести исторические инструкции в docs/archive только с исправлением ссылок.
6. Зафиксировать зависимости отдельно для GUI, бота/сервиса и provider workers. Использовать lock/constraints проверенного набора, а не бесконтрольное обновление на пользовательском ПК.
7. Ввести CONTRIBUTING/README: запуск, тесты, сборка, секреты, структура, резервирование и восстановление.

Критерий: чистый clone позволяет восстановить окружение по инструкции, не требует файлов с личного ПК разработчика и не содержит токенов или музыки.

## 6. Этап 1 — локальный Telegram-бот (MVP)

### Входит
- Приватный доступ по allowlist числовых Telegram user_id, не username.
- /start, /help, /search, /queue, /cancel, /settings; обычное текстовое сообщение запускает поиск.
- Поиск по названию/исполнителю и прямым ссылкам разрешённых провайдеров.
- Выдача по 5–10 результатов с пагинацией: исполнитель, название, версия, длительность, источник и доступность.
- Кнопки «Получить аудио», «Другой источник», «Отменить», «Назад».
- Понятные этапы задания: очередь → поиск аудио → загрузка → обработка → отправка → готово/ошибка/отмена.
- Отдельные лимиты поиска и получения аудио; при старте до 2 параллельных получений аудио и 1 конвертации, значения конфигурируются.
- Кеш метаданных и небольшой ограниченный кеш аудио с TTL, пределом диска и очисткой временных файлов.
- Дедупликация запросов одного файла/формата и повторов Telegram update/callback. Повторный callback не запускает ещё одну загрузку.
- После перезапуска задания не пропадают: незавершённые попытки получают корректный статус или ограниченный повтор.
- Повторная отправка через file_id там, где применимо. file_id привязан к боту, не универсален и не заменяет собственную модель AudioAsset. [^https://core.telegram.org/bots/api#sendaudio]
- Журналы без токенов, cookies, подписанных медиа-URL и текста приватных запросов по умолчанию.

### Форматы Telegram и плеера

Разделить **original asset** и **telegram delivery asset**. По документации sendAudio принимает MP3/M4A, до 50 МБ; другие контейнеры/большой размер требуют отдельного сценария. Сами лимиты необходимо перепроверять перед выпуском. [^https://core.telegram.org/bots/api/methods/sendaudio.md]

Пример: исходный Opus/WebM сохраняется для плеера; бот предлагает отправить документом, либо явно выбранную совместимую копию. Remux в M4A без потери качества допускается только для совместимого кодека; иначе нужна конвертация. Нельзя молча перекодировать оригинал или обещать проигрывание любого исходного контейнера встроенным Telegram-плеером.

Для файлов за пределами лимита выдавать понятное действие: другая доставка/формат либо ссылка с ограниченным доступом после появления сервера. Не поднимать Local Bot API Server только ради MVP: это отдельный компонент с издержками. У него другие лимиты, чем у облачного Bot API. [^https://core.telegram.org/bots/api]

### Не входит в первый MVP

Распознавание по отрывку, тексты песен, чарты, массовое скачивание дискографий, рекомендации, публичный доступ всем, Android. Приём присланных пользователем аудиофайлов — отдельная следующая задача с проверкой лимитов getFile, формата, размера и содержимого; не считать любые Telegram-вложения автоматически безопасными.

### Приёмка

Установка по README на Windows, запуск без публичного порта; доступ только владельцу; релевантный поиск; успешная доставка разрешённого тестового файла; отказ недоступного источника; отмена; повторный запрос; восстановление после перезапуска; нет зависания меню при загрузке.

## 7. Этап 2 — перенос бота на сервер в РФ

- Контейнеризировать приложение, нативные компоненты и конфигурацию; переиспользовать те же адаптеры и схемы данных.
- На старте long polling остаётся: webhook не обязателен. Один активный polling-процесс на токен; остановить локальный перед серверным запуском.
- До покупки длительного тарифа провести тест доступа к Telegram, выбранным каталогам и аудиоисточникам с конкретного VPS/IP. Домашняя сеть и дата-центр могут иметь разные ограничения. Статья-пример тоже описывает проблему доступа с VPS, но не является доказательством доступности каких-либо API сегодня. [^https://vc.ru/id5989840/2954344-telegram-bot-dlya-proslushivaniya-muzyki-bez-tsenzury]
- Ориентир для тестового VPS: 2 vCPU, 2–4 ГБ RAM и SSD от 20 ГБ при небольшом временном кеше; уточнить по измеренной нагрузке. Это не проверенный сайзинг и не обещание тарифа. GPU не нужен для первого этапа.
- Проверить лимит и стоимость исходящего трафика, диск, резервирование, правила хостинга, возможность нужных сетевых соединений. Скачивание пользователю через сервер может означать несколько передач одного файла.
- Настроить автоматический перезапуск, лимиты CPU/RAM, ротацию логов, контроль свободного места, healthcheck без обращения к провайдерам.
- Разделить состояние БД и расходуемый кеш. Регулярный зашифрованный backup БД/настроек и контрольный restore. Музыкальный кеш не считать постоянной облачной библиотекой.
- Контейнер без root, минимальные права, лимиты процессов и времени, закрытые внутренние порты.
- HTTPS нужен при появлении публичного API для плеера. БД и worker API наружу не выставлять.

Приёмка: контрольный прогон 72 часа, перезагрузка сервера, восстановление копии, ограничение диска, изоляция нескольких пользователей, подтверждённые live-проверки доступных источников. Успех локального бота сам по себе не разрешает выпуск серверной версии.

## 8. Этап 3 — интеграция с Windows-плеером

Плеер уже содержит способы скачивания: задача — объединить и улучшить их, а не создавать ещё один независимый загрузчик.

### Режимы
- **Локальный:** сохранённые файлы работают без сервера; при включённом интернете возможны локальные адаптеры.
- **Серверный:** поиск и подготовка на сервере, плеер получает метаданные и результат.
- **Авто:** явное отображение выбранного режима; управляемый fallback без бесконечного повторения одного источника.

### Привязка и доставка
- Плеер сам создаёт исходящее HTTPS-соединение. Нельзя публиковать текущий локальный API на порту 8765 в интернет.
- Привязка через одноразовый код с коротким TTL и явным подтверждением владельца; отдельный отзываемый токен на устройство.
- В боте появится «Добавить в плеер» и выбор устройства/плейлиста.
- Выключенный ПК: задание хранится на сервере. Отличать «задание принято», «файл подготовлен» и «сохранено на ПК».
- Доставка at-least-once с идемпотентной записью по delivery_id/hash: повтор не должен добавлять дубли. Не обещать exactly-once по сети.
- Обладание job_id или track_id не даёт права доступа: проверять пользователя/устройство на каждой операции.
- Скачивать в .part, проверять содержимое/размер/хеш, атомарно переименовывать; проверка свободного места и понятная ошибка.
- Возобновление поддерживать там, где сервер/источник действительно поддерживает Range; иначе корректно начинать заново.
- После сохранения файла атомарно обновлять библиотеку и отправлять подтверждение; обновление программы не удаляет пользовательские файлы.

### Предлагаемый API v1

```text
POST   /v1/search-jobs
GET    /v1/jobs/{id}
POST   /v1/download-jobs
POST   /v1/jobs/{id}/cancel
POST   /v1/device-pairings
POST   /v1/device-pairings/{id}/confirm
GET    /v1/devices/me/deliveries
POST   /v1/deliveries/{id}/ack
GET    /v1/assets/{id}/content
```

Все remote-маршруты требуют авторизации в соответствии с назначением; pairing имеет собственный ограниченный протокол. Короткоживущий доступ к файлам, лимиты и запрет на утечку чужих файлов. Истекающие URL обновляются. Основной транспорт статусов — polling/long polling; WebSocket вводить при необходимости, а не как обязательное усложнение MVP.

Приёмка: добавление из бота на включённый/выключенный ПК, повтор доставки, сеть оборвалась, файл уже существует, диск заполнен, сервер недоступен, отозванный токен; локальное воспроизведение продолжает работать.

## 9. Этап 4 — интерфейс и производительность desktop

Сначала функциональные прототипы и измерения, затем визуальная доработка. Не совмещать миграцию данных, смену UI-фреймворка и новый аудиодвижок в одной большой переделке.

### Интерфейс
- Главная: продолжить прослушивание, недавно добавленное, плейлисты, состояние загрузок; миксы позже.
- Раздел поиска: результат по готовности, пагинация, точная версия записи и источник, видимый формат/качество.
- Менеджер загрузок: этапы, скорость передачи при наличии данных, повтор, отмена, место сохранения. Не показывать фиктивный процент без известного объёма.
- Скелетоны вместо блокировки экрана, debounce поиска, отмена устаревшего запроса, виртуальные списки и ограниченный кеш обложек.
- Согласованные отступы, типографика, темы и иконки; клавиатурная навигация, фокус, масштабирование Windows, reduced motion.
- Ошибки понятны пользователю и имеют диагностический код. Не включать URL с секретами в сообщение.
- Сохранить мини-плеер, трей, эквалайзер, плейлисты и рабочие сценарии текущего приложения.

### Данные и горячие пути
- SQLite вместо монолитного JSON для растущей библиотеки, миграция с резервной копией и проверкой количества записей/плейлистов/путей.
- Миграция повторно безопасна, транзакционна, версионирована. Понижение версии приложения не должно молча портить новую БД.
- Инкрементальное чтение метаданных по mtime/size, ограниченная фоновая очередь, без полного пересканирования при каждом открытии.
- Измерить блокировки VLC, потоки и вызовы Python↔JS; сетевые и дисковые операции не выполняются в UI-потоке или под длительной общей блокировкой.
- Постоянные изолированные воркеры вводить лишь если процессный cold start подтверждён как заметное узкое место; предусмотреть перезапуск и очистку их состояния.

### Предварительные цели, не текущие результаты

Измерять на ПК пользователя: RTX 4060 Laptop, 32 ГБ RAM, SSD, Windows x64; фиксировать CPU, версии системы, размер окна, фоновые задачи и режим питания.

| Метрика | Предварительная цель |
|---|---|
| Первое окно и готовность UI | Отдельные измерения; ориентир готовности ≤3 с на согласованной библиотеке |
| Реакция локальных кнопок | p95 ≤100 мс до визуального отклика; не путать с запуском звука |
| Локальный индексированный поиск на 25 000 записей | p95 ≤200 мс после готовности индекса, без debounce |
| Прокрутка | Цель 60 Гц; анализ распределения frame time и кадров >50 мс, не только среднего FPS |
| Первый результат сети | Измерять отдельно cache hit/miss; ориентир p50 ≤3 с при доступном провайдере, не гарантия сети |
| Блокировка UI из-за сети | Не допускается независимо от скорости источника |
| Длительный прогон | Не менее 4 часов без падения/зависания; анализ тренда RAM/процессов, не произвольный норматив памяти |

Наборы: 1 000 / 10 000 / 25 000 реальных или репрезентативных записей; 100 000 — отдельный стресс-тест, не уже заявленная поддержка. Для повторных быстрых операций до 100 прогонов, для дорогих — не менее 20–30 с указанием размера выборки; p95 малой выборки трактовать осторожно.

Измерять холодный и тёплый старт, длительность до реального звука, чтение тегов и импорт отдельно от готового DOM. Не переносить результаты mocked Chromium напрямую на реальный WebView2. Live-проверки источников отделить от воспроизводимого CI без сети.

## 10. Этап 5 — автономная Windows-упаковка

Этот этап проверять с самого начала архитектуры: будущие адаптеры не должны делать автономный выпуск невозможным. Финальная упаковка после стабилизации функциональности.

- Windows x64-сборка на Windows runner/ПК, фиксированные версии и воспроизводимый рецепт.
- PyInstaller onedir; отдельные приватные embedded CPython для конфликтующих provider-зависимостей; не копировать venv разработчика.
- В комплекте необходимые VLC/plugins, FFmpeg/ffprobe, Deno/EJS, Fixed WebView2 и redistributable выбранных зависимостей.
- Проверять дополнительные системные prerequisites, например .NET/VC++ для конкретной pywebview/native-сборки. Если они требуются, включить допустимую поставку/явную обработку и проверить чистую Windows; не выдавать комплект за автономный по списку файлов.
- Inno Setup создаёт ярлыки и удаление. На машине пользователя не выполняются pip/winget и установка системного Python.
- Portable: распаковать всю папку и запустить EXE. Данные по умолчанию в LOCALAPPDATA; «всё хранится рядом с EXE» — отдельный режим, не предполагать его автоматически.
- Обновления не удаляют пользовательскую библиотеку; понятная политика несовместимых миграций.
- Проверки --check-runtime/--smoke-test необходимы, но недостаточны: чистая Windows без Python/VLC/FFmpeg/Deno/WebView2, кириллица и пробелы в пути, offline запуск локальной музыки, реальные звук/трей/мини-плеер/обновление/удаление.
- Подпись Authenticode желательна; неподписанный выпуск маркируется явно. Автообновление только после появления проверяемых подписанных релизов/манифеста и безопасного отката, не загрузка произвольного кода.
- В релизе LICENSE/THIRD_PARTY_NOTICES и необходимые исходники/предложения исходников по применимым лицензиям. Приватный GitHub сам по себе не решает требования распространения.

Приёмка: оба артефакта Setup и portable прошли чистую Windows; хеши и версии сохранены; автономность подтверждена, а не предполагается.

## 11. Будущие этапы, не часть первого бота

1. **Микс/открытия:** история с согласия пользователя; сначала метаданные/личные сигналы, затем опциональные аудиопризнаки. Оценивать сохранения/пропуски, не только техническую скорость. Новые подборки не перезаписывают сохранённые плейлисты.
2. **Облачная библиотека:** явное решение, храним ли полные аудиофайлы или только метаданные. Квоты, удаление, backup, стоимость трафика и права.
3. **Android:** предварительный кандидат Kotlin + Jetpack Compose + Media3 + Room + WorkManager. Финальный выбор после согласования UI/режимов. С ПК переиспользуются API, идентификаторы, схемы и правила синхронизации, не Python/HTML UI целиком.
4. Синхронизация плейлистов и файлов через версии изменений, хеши и журнал; конфликты/удаления рассматриваются отдельно. Синхронизация не заменяет резервные копии.
5. Распознавание по аудио, тексты и чарты — независимые исследования источников/лицензий/стоимости.

## 12. Безопасность и границы получения аудио

- Только разрешённые сценарии и доступ, предоставленный источником/правообладателем. Личное использование не означает автоматическое разрешение скачивать любую запись.
- Не включать DRM-дешифрование, обход оплаты/авторизации, кражу cookies и чужих токенов. Если источник требует подписку или разрешение — показывать это честно.
- Allowlist провайдеров и безопасная обработка URL/редиректов; защита от SSRF, локальных адресов, file:// и cloud metadata endpoints на сервере, включая адреса в манифестах. yt-dlp/FFmpeg не получают произвольный URL пользователя без адаптера и ограничений.
- Воркеры с минимальными правами, лимитами времени/памяти/диска; запрет произвольных shell-команд и загрузки исполняемых компонентов во время пользовательской операции.
- Проверка фактического медиа, контейнера, размера и длительности; изоляция .part и безопасные имена файлов.
- Ключи BotFather, провайдеров, устройств и cookies вне Git; отсутствие секретов в frontend, crash reports и URL-логах. Удаление утёкшего секрета из последнего коммита не делает его безопасным: отозвать и заменить.
- По умолчанию личный бот; приглашения и квоты для нескольких пользователей. Библиотеки и задания изолированы по владельцу. Удаление личной истории/аккаунта должно быть предусмотрено до открытия многопользовательского доступа.

## 15. Git/GitHub и откат

Рекомендуется **один приватный monorepo** на начальном этапе: desktop, bot и общий сервис. Не перемещать код массово сразу; оформить общие пакеты после baseline.

Целевая, а не уже выполненная структура:

```text
apps/desktop/
apps/bot/
packages/music_core/
services/music_api/
tests/
docs/
packaging/
infra/
.github/workflows/
```

Первичная последовательность, выполняется пользователем после backup и настройки ignore:

```powershell
git init
git status --short --untracked-files=all
git add --dry-run .
# Проверить список: нет токенов, cookies, музыки, venv, сборок и личных путей.
git add .
git diff --cached --stat
git diff --cached
# При необходимости остановиться и убрать лишнее из staging.
git commit -m "chore: baseline before telegram bot"
git branch -M main
```

Проверка diff вручную необходима, особенно для небольших файлов с токенами; перед push желательно secret scanning. Приватный репозиторий не делает утечку допустимой.

Создать пустой приватный репозиторий на GitHub и только затем:

```powershell
git remote add origin <URL_СВОЕГО_ПРИВАТНОГО_РЕПОЗИТОРИЯ>
git push -u origin main
git switch -c feature/telegram-bot
```

Не копировать placeholder URL буквально. Ветки: feature/telegram-bot, feature/player-integration, feature/library-sqlite, fix/windows-package. main содержит проверенный исходный baseline; «проверенный Windows-релиз» — отдельная отметка только после приёмки.

Безопасный откат завершённого изменения: `git revert <commit>` в чистом рабочем дереве. Для просмотра старой версии — отдельная ветка/worktree. Не советовать reset --hard или git clean -fdx как обычную очистку: они могут уничтожить незакоммиченные файлы и окружения.

Git хранит код, не облачную музыкальную библиотеку и не резервные копии данных пользователя. Музыку, кеши и релизные EXE держать вне истории; проверенные Setup/portable — GitHub Releases после проверки прав распространения, версий и хешей. У приватных Releases доступ также приватный.

## 16. Решения для согласования перед реализацией

Предлагаемые значения по умолчанию, не блокирующие написание ТЗ:
1. Название экосистемы — Slynor; бот сначала только для владельца.
2. Первая версия бота отправляет выбранное аудио в Telegram; связь с плеером появляется отдельным этапом.
3. Языки поиска — русский и английский; оригинальная версия записи важнее автоматического выбора любого похожего файла.
4. Исходное аудио для desktop; для Telegram явная политика совместимого файла/документа. Никакой скрытой конвертации.
5. Один приватный GitHub monorepo, музыка и секреты вне Git.
6. Сервер пока без постоянного хранения всей библиотеки; небольшая квота временного кеша. Провайдера/тариф выбирать после VPS-проверки.
7. Не менять UI-фреймворк и аудиодвижок без профилирования и отдельного обоснования.
8. Android, рекомендации и Shazam-подобное распознавание не входят в MVP бота.

**Следующий практический шаг после согласования:** резервная копия + Git baseline + короткий эксперимент источников. Не начинать с покупки долгого VPS-тарифа или добавления сразу всех библиотек.
